# offheap-gcra

Rate limiting библиотека для Java 22+, предлагающая альтернативный подход к учету частоты запросов в высоконагруженных сценариях. В основе проекта лежит алгоритм **GCRA** (Generic Cell Rate Algorithm) и хранение состояния в плоских буферах фиксированного размера без создания объектов в рантайме.

Поддерживаются две реализации: компактные массивы примитивов в куче (`long[]`) и размещение в нативной памяти вне кучи JVM с использованием Foreign Function & Memory API (JEP 454). Вся синхронизация реализована неблокирующим образом (lock-free) через атомарные CAS-операции над 64-битными примитивами. Проект не имеет внешних runtime-зависимостей и требует только стандартную библиотеку JDK 22.

## Архитектурная идея

Традиционные решения для rate limiting в экосистеме Java (такие как Bucket4j или Guava RateLimiter) обычно хранят состояние каждого клиента в виде одного или нескольких объектов в `ConcurrentHashMap`. При умеренном количестве ключей это практично, однако при сотнях тысяч или миллионах активных сущностей (например, при защите API-шлюза по IP-адресам) на каждый ключ накладываются расходы на заголовки объектов, ссылки и выравнивание памяти. В результате полезные 16 байт данных разрастаются до 150–200 байт на ключ, а миллионы мелких объектов нагружают сборщик мусора при сканировании графа живых ссылок.

В `offheap-gcra` предлагается другой путь: отказаться от ссылочных структур и объектов-оберток в пользу фиксированной таблицы открытой адресации. Все данные одного ключа занимают ровно 24 байта, распределенные по трем непрерывным параллельным буферам: ключ, упакованная ячейка состояния и метка времени последнего обращения. Это позволяет либо работать с плоскими массивами `long[]`, которые JVM оптимизирует эффективнее всего, либо полностью вынести таблицу за пределы кучи через FFM `Arena.ofShared()`, разгружая heap dump и профиль памяти сервиса.

## Алгоритм GCRA и математическая модель

В отличие от классического Token Bucket, где требуется вычислять начисление токенов, алгоритм Generic Cell Rate Algorithm (GCRA) сводит все состояние лимитера для конкретного ключа к одной точке во времени — **TAT** (Theoretical Arrival Time, теоретическое время прибытия следующего запроса).

Поведение алгоритма задается двумя величинами:
- $T$ (`interval`) — расчетный интервал между запросами при равномерной нагрузке.
- $\tau$ (`burstTolerance`) — допустимый всплеск (толерантность к пачкам).

Вместимость пачки $B$ в привычных терминах Token Bucket определяется отношением толерантности к интервалу:

$$B = \left\lfloor \frac{\tau}{T} \right\rfloor + 1$$

Когда запрос поступает в физический момент времени $t$, лимитер сравнивает текущее время с сохраненным значением $\text{TAT}$:

$$t < \text{TAT} - \tau$$

Если это неравенство истинно, лимит считается превышенным, запрос отклоняется, а $\text{TAT}$ остается неизменным. Время, через которое клиент сможет повторить попытку, равно $(\text{TAT} - \tau - t)$.

Если же текущее время удовлетворяет допустимому окну ($t \ge \text{TAT} - \tau$), запрос разрешается, а новое значение $\text{TAT}_{\text{new}}$ сдвигается вперед:

$$\text{TAT}_{\text{new}} = \max(\text{TAT}, t) + T$$

Для lock-free реализации такая модель удобна тем, что всё состояние ключа представляет собой одно число. Переход от предыдущего состояния к следующему вычисляется тривиальной арифметикой и фиксируется одной инструкцией CAS без использования мьютексов.

## Структура памяти и упаковка данных

Хранилище организовано как хеш-таблица с открытой адресацией размером `capacity` (степень двойки). Состояние распределено по трем параллельным структурам: `keys` (идентификатор), `cells` (упакованное состояние и время) и `lastAccess` (метка времени для фоновой эвикции). На один слот приходится ровно 24 байта: таблица на $65\,536$ слотов требует около 1.5 МБ памяти, а на $1\,048\,576$ слотов — ровно 24 МБ.

### Разметка 64-битной ячейки

Чтобы обновление статуса слота и времени TAT выполнялось неделимо, оба значения упакованы в одно 64-битное слово `long`:

```
 63   61 60                                                           0
+-------+-------------------------------------------------------------+
| STATE |                Theoretical Arrival Time (TAT)               |
+-------+-------------------------------------------------------------+
 3 бита                             61 бит
```

Три старших бита кодируют фазу жизненного цикла ячейки:
- `0 (EMPTY)` — свободная ячейка.
- `1 (CLAIMING)` — резервирование ячейки новым потоком.
- `2 (OCCUPIED)` — активная запись, содержащая актуальный TAT.
- `3 (EVICTING)` — промежуточная фаза удаления неактивной записи.
- `4 (TOMBSTONE)` — удаленная ячейка, сохраняющая связность цепочки поиска.

Младшие 61 бит отведены под монотонное время в наносекундах (`System.nanoTime() - BASE`). Такого диапазона хватает примерно на 73 года непрерывной работы процесса без риска переполнения счетчика.

### Разрешение коллизий и Tombstones

Поиск слота выполняется линейным пробингом по маске хеша. При удалении устаревших записей слот нельзя сбрасывать в `EMPTY`, поскольку это разорвало бы цепочку поиска для других ключей, смещенных далее по таблице из-за первичных коллизий.

Вместо этого освобождающийся слот переводится в статус `TOMBSTONE`. Поисковый алгоритм проходит сквозь такие слоты до первого `EMPTY`, гарантируя нахождение существующей записи. При вставке нового ключа поток проверяет цепочку до первого `EMPTY` (исключая появление дубликата ключа в другом месте таблицы) и занимает первый встретившийся `TOMBSTONE` через атомарный CAS.

## Результат операции (`AcquireResult`)

Стандартный булев интерфейс `tryAcquire` не позволяет вызывающей стороне отличить ситуацию, когда клиент действительно превысил разрешенную частоту запросов, от ситуации, когда таблица заполнена на 100% и не может выделить слот под новый ключ. В сетевом шлюзе возврат `false` во втором случае привел бы к отправке ошибочного кода `HTTP 429 Too Many Requests`.

Для точной диагностики метод `acquire` возвращает перечисление `AcquireResult`:
- `ACQUIRED` — запрос разрешен.
- `RATE_LIMITED` — лимит частоты превышен клиентом (HTTP 429).
- `CAPACITY_EXHAUSTED` — таблица переполнена, свободные слоты отсутствуют (ошибка инфраструктуры, например HTTP 503).

Метод `tryAcquire(key)` сохранен для быстрых сценариев, где достаточно простой булевой проверки, и возвращает `true` строго при значении `ACQUIRED`.

## Жизненный цикл и управление ресурсами

Для координации остановки лимитера используется трехфазный статус: `OPEN -> CLOSING -> CLOSED`. Вызов `close()` атомарно переводит объект в состояние `CLOSING`, отменяет задачи фоновой эвикции и освобождает нативную память `Arena`. Все параллельные и последующие вызовы `tryAcquire()` после закрытия детерминированно завершаются выбрасыванием `IllegalStateException`.

Лимитер не навязывает создание отдельных потоков под каждый экземпляр. Очистка устаревших слотов по умолчанию выполняется вручную через вызов `clean()`. При необходимости автоматической эвикции метод `scheduleEviction(Duration)` подключает лимитер к общему планировщику `CleanerScheduler.shared()`, который обслуживает все экземпляры библиотеки единственным потоком-демоном.

## Примеры использования

### Базовый сценарий с Duration

```java
import ru.kutkovmax.AcquireResult;
import ru.kutkovmax.LockFreeGcraLimiter;

import java.time.Duration;

// Создание off-heap таблицы:
// 65 536 ключей (степень двойки)
// 50 запросов в секунду (интервал 20 мс)
// Пачка до 5 запросов (толерантность 100 мс)
// Удаление неактивных ключей через 60 секунд
try (LockFreeGcraLimiter limiter = LockFreeGcraLimiter.offHeap(
        65_536,
        Duration.ofMillis(20),
        Duration.ofMillis(100),
        Duration.ofSeconds(60)
)) {
    // Опциональное фоновое удаление устаревших ключей каждые 10 секунд
    limiter.scheduleEviction(Duration.ofSeconds(10));

    long key = 100500L;

    // Быстрый булев путь
    if (limiter.tryAcquire(key)) {
        processRequest();
    }

    // Проверка с дифференциацией ошибок
    AcquireResult result = limiter.acquire(key);
    switch (result) {
        case ACQUIRED -> processRequest();
        case RATE_LIMITED -> respond(429);
        case CAPACITY_EXHAUSTED -> respond(503);
    }
}
```

### Низкоуровневый вызов в наносекундах

Для критичных к задержкам путей предусмотрены перегрузки, принимающие примитивные параметры без создания объектов `Duration`:

```java
LockFreeGcraLimiter limiter = LockFreeGcraLimiter.offHeap(
        65_536,         // capacity
        20_000_000L,    // intervalNanos (20 мс)
        100_000_000L,   // burstToleranceNanos (100 мс)
        60_000_000_000L // evictionTimeoutNanos (60 с)
);
```

## Сравнение Heap и Off-Heap

Проект включает бенчмарк `HeapVsOffHeapComparison` на емкости в 65 536 слотов (Adoptium Temurin 22.0.2, Windows):

| Бэкенд | Нагрузка | Потоки | Throughput | p50 | p99 | p99.9 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **HEAP** | 1 ключ (contention) | 1 | 8.4 млн op/s | 100 ns | 1.0 мкс | 4.2 мкс |
| **OFF-HEAP** | 1 ключ (contention) | 1 | 6.5 млн op/s | 100 ns | 0.3 мкс | 1.4 мкс |
| **HEAP** | 10 000 разных ключей | 4 | 9.8 млн op/s | 100 ns | 2.4 мкс | 8.9 мкс |
| **OFF-HEAP** | 10 000 разных ключей | 4 | 8.3 млн op/s | 100 ns | 2.7 мкс | 15.3 мкс |
| **HEAP** | 10 000 разных ключей | 16 | **23.9 млн op/s** | 100 ns | 0.7 мкс | 2.6 мкс |
| **OFF-HEAP** | 10 000 разных ключей | 16 | **20.1 млн op/s** | 100 ns | 0.7 мкс | 2.7 мкс |

Результаты показывают, что вариант на куче (`long[]`) опережает off-heap на 10–15% по абсолютной пропускной способности, поскольку доступ к плоскому примитивному массиву компилятор JIT оптимизирует эффективнее, чем вызовы через `MemorySegment`. 

Смысл off-heap варианта заключается не в ускорении одиночной операции, а в изоляции больших объемов состояния: при миллионах записей вынесение данных за пределы кучи сохраняет компактный размер heap dump при анализе профиля приложения и позволяет исследовать практическое поведение FFM API под реальной многопоточной нагрузкой.

Для открытой адресации оптимально поддерживать коэффициент заполнения таблицы не выше 0.70. При ожидании порядка 40 000 одновременно активных ключей рекомендуется выбирать размер таблицы $65\,536$.

## Тестирование и верификация

Надежность алгоритма проверяется на нескольких уровнях:
- Набор из 114 модульных тестов на JUnit 5, охватывающий расчет интервалов GCRA, битовые операции, эвикцию записей из середины кластера коллизий и работу с пограничными значениями.
- Стресс-тесты конкурентности на базе JCStress (`SameKeyStressTest`, `EvictionRaceStressTest`, `CloseRaceStressTest`), подтверждающие отсутствие потери обновлений, корректность параллельной эвикции и безопасность вызова `close()`.
- Бенчмарки на базе JMH (`GcraBenchmark`).

Запуск тестов:
```bash
./mvnw test        # Linux / macOS
mvnw.cmd test      # Windows
```
